## 3. ⚠️ 本轮最重要的发现：瓶颈是 **decode**，不是 prefill（修正 P1 全系列归因）

实测把单次调用拆开看：

```
A 组：load 29.64 s │ prefill 2.61 s（3.0%） │ decode 54.26 s（62.7%）
```

**prefill 只占 2.61 秒，decode 占了 54.26 秒。**

### 这对 P1 系列结论的修正

P1-2 / P1-3 把瓶颈表述为「**固定 prefill 成本**」，其经验依据是「文档体量缩到 1/4000，单篇耗时只降到 1/5」。
现在看，**该现象的成因不是 prefill 而是 decode**：

- **输出 token 数与输入体量基本无关**（抽取总是产出大致相同条数的实体/关系 + 描述）
- 而 decode 速率只有 **4.7 tok/s** ⇒ 每篇成本 ≈ `固定输出 token 数 ÷ 4.7`
- ⇒ 「文档变大/变小，耗时变化不大」被正确观测，但**归因错了**：固定的是**输出长度 × 极慢的 decode 速率**

### 这也解释了此前几条"看起来反直觉"的实测

| 前序实测 | 用 decode-bound 解释 |
|---|---|
| P1-2 `MAX_GLEANING=0` 调用数减半但墙钟未改善 | 减的是"第 2 次调用"，而每次调用的 decode 时长方差大；**减调用数不减单次 decode** |
| P1-3 batch insert 收益 0.0045% | batch 只动入队开销，**与 decode 无关** |
| Prompt 裁剪上限 6.5% | 裁 prompt 只降 prefill（占 3%），**天花板自然极低** —— 与实测自洽 |

**⇒ 修正后的瓶颈表述：`单次调用的输出 token 数 ÷ decode 速率`，根因是 8B 在 6 GB 卡上的层卸载拖慢 decode。**

## 4. 为什么本杠杆的收益有上限（机制说明）

KV 量化确实生效了（`size` 5.97 → 5.67 GB），却只把卸载从 29.5% 压到 25.1%，**没有清零**。原因：

| VRAM 组成 | 体量 | 可否被 KV 量化影响 |
|---|---|---|
| **模型权重**（4-bit 量化后） | **≈4.87 GiB** | ❌ **不受影响** |
| KV cache @4096 | ≈0.5 GiB (f16) → ≈0.25 GiB (q8_0) | ✅ 减半 |
| 计算缓冲等 | 其余 | ❌ |

**可用显存 5.0 GiB vs 权重 4.87 GiB** ⇒ 结构性欠配。KV 只占全部占用的一小部分，**所以 KV 量化的收益上界就是十几到二十几个百分点**，不可能达到 2×。

**实测即证**：decode +21.3%、端到端 **−8.1%**。

1. **推荐进入 Step 2 配对 A/B** —— 因为 Step 1 已证明机制有效（卸载下降、decode 变快），
   而未验证的那一项（质量）**正是 Step 2 的验收内容**，两者正好接续。

   真正的 2× 级提升需要动"权重体积 vs 5.0 GiB"这一结构性矛盾（换更小权重/更多显存/云端），
   而 `qwen3:4b` 已验证不可用、云端按指示暂停 ⇒ **短期内可获得的只有这十几 %**。

   注意它按"每次会话"计，量级与本次 decode 优化相当。
