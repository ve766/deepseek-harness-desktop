## 0. Revision / Errata（2026-09-11，P1-4B Step 1 实测后更正）

> ⚠️ **本节修正 §2 的瓶颈归因。原文（含旧结论）按"保留历史证据"要求原样保留在下文，未删除。**

### 0.1 被修正的结论

| # | 旧结论（错误） | 位置 | 更正后 |
|---|---|---|---|
| **E1** | **瓶颈 = 单次调用的固定 *prefill* 成本** | §2 标题 / §2 证据链 / §2 三个"不是" | **瓶颈 = 单次调用的 *decode* 阶段耗时** |

### 0.2 更正的依据（P1-4B Step 1 直接实测，非推断）

用真实抽取 prompt（7,019 chars ≈1,755 tok）+ 256 tok 输出，读 Ollama 自报计时字段：

```
load 29.64 s │ prefill 2.61 s（占 3.0%）│ decode 54.26 s（占 62.7%）
              prefill 579 tok/s          decode 仅 4.7 tok/s
```

| 事实 | 值 |
|---|---|
| **prefill 占比** | **≈3%** |
| **decode 占比** | **≈60%+** |
| `qwen3:8b` 层卸载 | **GPU 70.5% / CPU 29.5%**（实测，非估计） |
| **主要成本由什么决定** | **输出 token 数量 ÷ decode 速率（4.7 tok/s）** |
| 可用显存 vs 权重 | 5.0 GiB vs **4.87 GiB** ⇒ KV 量化无法清零卸载 |

### 0.3 为什么旧结论看起来"有道理"（诚实记录）

P1-3 观测到「文档体量缩到 1/4000，单篇耗时只降到 1/5」，据此推断"固定开销 = prefill"。
**该观测本身正确，但归因错了**：真正的固定项是**输出 token 长度** —— 抽取产出的实体/关系条数与描述长度
**与输入文档大小基本无关**，因此每篇成本 ≈ `固定输出 token 数 ÷ 4.7 tok/s`。

### 0.4 更正后与既有实测的自洽性（修正使解释力更强）

| 前序实测 | 用"decode 主导"解释 |
|---|---|
| P1-2 `MAX_GLEANING=0` 调用数减半但墙钟未改善 | 减少的是"第 2 次调用"，**单次 decode 时长与方差未变** |
| P1-3 batch insert 收益 0.0045% | batch 只动入队开销，**与 decode 无关** |
| P1-3 文档体量 1/4000 → 时间 1/5 | 输出长度基本不变 ⇒ 时间自然变化不大 |
| Prompt 裁剪上限仅 6.5% | 裁 prompt 只降 prefill（占 3%）⇒ **天花板必然极低** |

### 0.5 对优化方向的影响

- **prefill 类优化**（缩 prompt / 降 chunk）**天花板极低** —— 已被本更正解释
- **decode 类优化**才是有效方向：降低层卸载（`FLASH_ATTENTION` + `KV_CACHE_TYPE=q8_0`）、
  减少输出 token 数、或换更小权重/更多显存（结构性）
- §3「已排除的路径」结论**不变**（排除理由仍然成立）

## 2. 当前瓶颈结论（P1 三次独立实测收敛）

> ❌ **【本节结论已被 §0 Revision / Errata 更正】**：下方"**固定 prefill 成本**"的归因**不成立**。
> 正确表述是「**固定的是输出 token 长度 × 极慢的 decode 速率（4.7 tok/s）**」；prefill 仅占约 3%，decode 占 60%+。
> **以下原文保留为历史证据，请勿据此行动。**

### 结论：瓶颈 = **LLM 单次调用的固定 prefill 成本 × 串行执行**

**证据链（三条独立证据指向同一结论）**：

| 来源 | 测试 | 观测 | 推论 |
|---|---|---|---|
| P1-2 | 抽取调用数减半（gleaning=0） | 墙钟**无改善**；单调用延迟方差 169 → 410 s/call，吞掉 2× 理论收益 | 瓶颈**不是调用次数** |
| P1-3 | 请求合并（6 次 → 1 次） | 仅省 34.8 ms；HTTP/入队开销占墙钟 **0.022%** | 瓶颈**不是 HTTP/入队开销** |
| P1-3 | 文档体量缩到 **1/4000** | 单篇耗时仅降到 **1/5**（1020 s → 146 s） | 成本由**固定开销**主导，**不是内容量** |

**固定开销构成**：

| 组成 | 体量 |
|---|---|
| `entity_extraction_system_prompt` | ≈1,800 tokens（固定，与文档无关） |
| chunk（`chunk_token_size` 默认 1200） | ≈1,200 tokens |
| **合计** | **≈3,000 / `num_ctx` = 4096** → 输出预算仅余约 1,000 token |

**硬件约束**：RTX 3060 Laptop **6 GB** 显存；`qwen3:8b` 权重 5.23 GB → 驻留已近满，约 30% 层 CPU 卸载 → 近满窗 prompt 的 prefill 成本极高。

### 三个"不是"（P1 净产出）

- **不是** HTTP / 入队开销 → P1-3 实测占 0.0045%
- **不是** 调用次数 / gleaning → P1-2 实测减半无效
- **不是** 文档体量 → P1-3 实测体量 1/4000 仅换得时间 1/5

→ 是 **单次调用的固定 prefill 成本 × 串行度**。
