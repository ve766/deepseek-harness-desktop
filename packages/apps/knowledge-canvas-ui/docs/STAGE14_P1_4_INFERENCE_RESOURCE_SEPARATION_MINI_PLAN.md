## 1. 问题定义

P1 三轮实测已把瓶颈钉死为 **LLM 单次调用的固定 prefill 成本 × 串行执行**，并排除了 gleaning、batch、prompt 裁剪三条路。

P1-4 的问题重新定义为：**瓶颈是否部分由「推理资源争用」造成，以及如何隔离？**

具体三个子问题：

- **Q1** 当前 `qwen3:8b` + `nomic-embed-text` 在 RTX 3060 6GB 上的显存占用与换入换出机制是什么？
- **Q2** embedding 与 extraction 是否存在**显存竞争证据**？
- **Q3** 把 **embedding 外置**能否降低 extraction 单次调用延迟？是否存在**保持 Ollama 闭环的低风险本地方案**？是否值得引入云端？

## 2. 证据（只读实测，2026-09-11）

### 2.1 显存事实

| 项 | 值 | 来源 |
|---|---|---|
| GPU | NVIDIA RTX 3060 Laptop，**total 6144 MiB = 6.0 GiB** | `nvidia-smi` |
| 当前占用 | 38 MiB used / 5959 MiB free（空闲） | `nvidia-smi` |
| **Ollama 可见显存** | **`total="6.0 GiB" available="5.0 GiB"`** | Ollama `server.log` |
| **Ollama 推导的 ctx** | `msg="vram-based default context" total_vram="6.0 GiB" default_num_ctx=4096` | Ollama `server.log` |
| 集显 | 被 Ollama 忽略（`dropping integrated GPU`，Intel UHD） | Ollama `server.log` |
| Ollama 版本 | **0.32.5** | `/api/version` |
| `qwen3:8b` 权重 | **5.23 GB = 4.87 GiB** | `/api/tags` |
| `nomic-embed-text` | 0.27 GB（embed ctx 8192） | `/api/tags` + LightRAG 日志 |
| `qwen3:4b` | **2.50 GB = 2.33 GiB** | `/api/tags` |
| `OLLAMA_*` 环境变量 | **仅 `OLLAMA_MODELS=F:\ollama model`**；`MAX_LOADED_MODELS` / `KV_CACHE_TYPE` / `FLASH_ATTENTION` / `NUM_PARALLEL` **均未设置**（走默认） | 环境变量 |

> ⚠️ **关键事实**：Ollama 只拿到 **5.0 GiB 可用显存**（6.0 GiB 中被系统/显示占用约 1 GiB）。
> 而 `qwen3:8b` 权重 **4.87 GiB** —— 仅权重就吃掉可用量的 **97%**，留给 KV cache 与计算缓冲仅 **≈0.13 GiB**。

### 2.2 换入换出机制 —— 两个独立机制（必须分开看）

**M1｜静态"放不下"（常驻欠配）**
- 权重 4.87 GiB + KV cache（4096 ctx，8B）≈ 0.4–0.6 GiB + 计算缓冲 ⇒ **需求 ≈5.3–5.5 GiB > 可用 5.0 GiB**
- ⇒ **结构性 CPU 卸载不可避免**（部分层常驻 CPU）→ prefill 极慢 → 这正是 P1-2/P1-3 实测的 **169–410 s/call** 与 **50–67% 失败率**的直接来源。

**M2｜动态"换模型抖动"（本文档新增发现）**
- LightRAG 每篇的处理序列为：`Processing 1 document` → **extract（LLM ×2）** → **`Upserting relation VDB`（embedding）** → pipeline 停止
- 即 **同一篇内先 LLM 后 embedding 交替**；而 `qwen3:8b`(4.87 GiB) + `nomic-embed-text`(0.25 GiB) + 各自 KV/缓冲 **远超 5.0 GiB 可用**
- ⇒ 两者**无法同时驻留**，Ollama 必须**卸载 8B → 载入 embedder → 再卸载 → 重新载入 8B**，逐篇循环。

> **结论**：瓶颈主体是 **M1**；M2 是叠加在 M1 之上的**额外**成本。
> ⚠️ **重要推论**：**仅把 embedding 外置只能消除 M2，不能消除 M1** —— 因此 embedding 外置的收益上界 = 重载开销，而非 169–410 s/call 的主体。

### 2.3 embedding 与 extraction 的竞争证据

| # | 证据 | 强度 |
|---|---|---|
| E1 | **容量算术**：可用 5.0 GiB < 8B 权重+KV 需求 → 单模型已欠配 | 强（可复算） |
| E2 | 8B(4.87)+embed(0.25)+KV ≈ 5.6–6.2 GiB > 5.0 GiB ⇒ 双模型**不可能共存** | 强（可复算） |
| E3 | **调用序列**：baseline 日志中每篇均为 extract → VDB upsert 交替（行 113 / 206,209 / 297–299 / 329） | 强（日志实测） |
| E4 | `OLLAMA_MAX_LOADED_MODELS` **未设置** ⇒ 走 Ollama 默认的容量驱动逐出策略；在可用显存不足时**必然逐出** | 中（配置实测 + 行为推断） |
| E5 | Ollama 日志中**未见**模型 load/unload 事件记录（该实例日志无模型加载行） | — （**不支持**直接观测，见 §2.4） |

### 2.4 未取得 / 不可取得的证据（诚实声明）

1. **未直接观测逐出事件**：需在模型加载期间执行 `ollama ps` 并读 Ollama 加载日志 —— 本轮的「不修改环境」边界下**未做**。故 M2 由 **E1–E4 推断**，非直接观测。
2. **「30% CPU 卸载」未复核**：该数字来自 P1-2 记录，本轮未加载模型故未复验；按 §2.1 算术只能确认"**部分卸载必然发生**"，**具体比例待实测**。
3. **F: 盘介质类型未知**：`wmic` 被本机安全策略禁用，无法只读判定 SSD/HDD。
   该项**直接决定 M2 的重载成本**（读 4.87 GiB：SSD 约 10–20 s；HDD 约 60–100 s/次）。**必须在实验前确认**。

## 3. 对 Q3 的直接回答

### 3.1 embedding 外置能否降低 extraction 单次调用延迟？

- **能，但幅度受限**：只消除 **M2（重载）**，**不消除 M1（卸载）**。
- 因此收益 ≈ 每篇省下 1 次 8B 重载（**SSD 约 10–20 s；HDD 约 60–100 s，视 F: 介质**）。
- 相对 P1-2 实测的单篇 **678–1020 s**：**SSD 情形约 2–3%，HDD 情形约 6–15%**（区间大，取决未确认项）。
- ⇒ **单独做 embedding 外置，大概率不够**；但它与"换更小抽取模型"**叠加**时价值显著（见 §4）。

### 3.2 是否存在保持 Ollama 闭环的低风险本地方案？

**存在，且是首选**：

| 方案 | 做法 | 是否需换模型 | 是否出网 | 预期 |
|---|---|---|---|---|
| **L1 换抽取模型为 `qwen3:4b`** | 仅改 `LLM_MODEL`（本地已有 2.50 GB） | 是（4B 替代 8B） | 否 | **消除 M1+M2**：2.33 GiB + 0.25 GiB ≈ 2.6 GiB ≪ 5.0 GiB ⇒ **两者全量常驻、零卸载零重载** |
| **L2 embedding 走 CPU** | 第二个 Ollama 实例（或 `num_gpu=0`）只跑 `nomic-embed-text`，抽取实例不再被逐出 | 否 | 否 | 仅消除 M2；CPU 侧 embedding 与 GPU 抽取**可并行** |
| L3 全流程分相（先全抽取后全嵌入） | 需改 LightRAG 源码 | — | — | **越红线**，不做 |
| L4 下调抽取 `num_ctx` | 现为 4096；prompt+chunk 已占 ≈2,955 tok | 否 | 否 | 空间极小，收益边际 |
| L5 云端 provider | 抽取外置到 API | 是 | **是** | 见 §4 |

**L1 是唯一同时消除 M1 与 M2 的方案**，且**完全本地、零新依赖、零出网**，直接命中 P1 确认的根因。

### 3.3 云端/API 方案是否值得引入？

| 维度 | 评估 |
|---|---|
| **成本** | 按 token 计费。粗算：单次调用 input ≈3,000 tok，2 call/chunk，长文 ~12 chunk ⇒ **≈7.2 万 tok/篇**。按主流 API 量级约 **每篇几美分**。⚠️ P1-2 已证 **gleaning=0 可令调用数减半 ⇒ 成本直接减半**，应纳入估算 |
| **隐私** | **决定性风险**：文档离开本机。知识库内容出网是**产品姿态变更**，不是工程取舍 —— **必须由产品决策**，不应由工程默认开启 |
| **稳定性** | ✅ 云 RTT 稳定（秒级）vs 本地 169–410 s/call ⇒ **可根治 50–67% 失败率** |
| **质量** | ✅ 前沿模型抽取质量**明显优于** qwen3:8b |
| **结论** | **不做默认**。P0-S1 已建好 provider profile seam（`providerConfig.ts`），**保留为 opt-in**：本地优先、云端可选 |

## 4. 候选方案总览（成本 / 隐私 / 稳定性 / 质量）

| 方案 | 延迟 | 隐私 | 稳定性 | 质量 | 闭环 | 改动面 |
|---|---|---|---|---|---|---|
| **L1 qwen3:4b** | **大改善** | ✅ 全本地 | 改善（不再卸载） | **需验证**（主要风险） | ✅ | 仅 `LLM_MODEL` |
| L2 embedding→CPU | 小–中改善 | ✅ 全本地 | 改善（不再逐出） | 不变 | ✅ | 加一个本地实例 |
| L4 ctx 微调 | 边际 | ✅ | 不变 | 不变 | ✅ | 仅 `.env` |
| L5 云端抽取 | **根治** | ❌ 出网 | ✅ | ✅ 提升 | ❌ | provider 切换 |
| L1+L2 叠加 | **最大** | ✅ | ✅ | 需验证 | ✅ | 两处配置 |

## 5. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| **L1 质量下降**（4B 抽取弱于 8B） | **中–高（主风险）** | 沿用 **≥基线 90% 质量门槛** 的配对 A/B（同 P1-2 口径） |
| M2 收益被延迟方差淹没 | 中 | P1-2 实测方差 2.4× ⇒ 必须**配对 + 多次采样**，不能单跑 |
| F: 为 HDD ⇒ 重载成本远高于预期 | 中 | **实验前先确认介质类型**（本机安全策略禁用 `wmic`，需你授权其它只读手段） |
| L2 引入第二实例造成端口/显存管理复杂 | 低 | 固定端口 + 只跑 embedding |
| L1 触发既有 Redis/图数据不兼容 | 低 | 抽取模型不改变 schema，仅影响抽取内容 |
| 云端隐私争议 | **高（若默认开启）** | **只做 opt-in，不改默认** |

## 6. 对 S13-C DP3（复用 `qwen3:8b`）的影响评估

**DP3 原意**：复用本地已有的 `qwen3:8b`，避免引入新模型/新依赖。

**评估**：DP3 **不算错，但欠规格**。

- ✅ 它达成的：复用现有模型、保持本地闭环、零新增依赖。
- ❌ 它未覆盖的：**未校验「8B 是否真的装得下」**。实测表明 **可用显存仅 5.0 GiB，而 8B 权重 4.87 GiB** ⇒ 结构性 CPU 卸载 ⇒ 169–410 s/call、**失败率 50–67%**。
- ⇒ DP3 的前提「本地 8B 可用」**只在"能跑"意义上成立，在"可用"意义上不成立**。

**建议：不推翻 DP3 的原则，只修订其模型选择。**

| 选项 | 是否保留 DP3 精神 | 评价 |
|---|---|---|
| 保持 `qwen3:8b` 不动 | ✅ | ❌ 已知不达标（延迟+可靠性） |
| **改为 `qwen3:4b`（推荐）** | ✅ **是** —— 同族、全本地、零新依赖 | ✅ 直接解决显存欠配 |
| 抽取迁云端 | ❌ **否**（打破本地闭环） | 仅作 opt-in |

> 即：**修订 = 把「复用 qwen3:8b」放宽为「复用 qwen3 系列、选尺寸匹配硬件者」**。这保留 DP3 的意图，同时修正其唯一失准处。

## 7. 推荐顺序

0. **先测量（不实现）**：加载 `qwen3:8b` 与 `qwen3:4b` 各一次，读 `ollama ps` 的 VRAM 拆分 + `nvidia-smi`，并确认 **F: 介质类型** 与 **M1/M2 成本拆分**。→ 把 §3.1 的区间收敛为定值。
1. **L1：`qwen3:4b` 配对 A/B**（延迟 + ≥90% 质量门槛）—— 预期收益最大、改动最小、完全本地。
2. **L2：embedding 外置到 CPU**（与 L1 叠加，或作为"必须保留 8B 时"的兜底）。
3. **L4：`num_ctx` 微调**（边际，可选）。
4. **L5：云端 opt-in**（仅在用户接受隐私取舍时；不设默认）。

---

## 8. 是否值得进入实验阶段

**值得 —— 但必须先走第 0 步「测量」，而不是直接实现。**

理由：
- P1 已排除 gleaning / batch / prompt 三条路，**资源隔离是剩下唯一有实证支撑的方向**；
- 本轮已发现**新的可测机制 M2（逐篇模型抖动）**，且 **M1/M2 的相对权重尚未量化** —— 不量化就实现，会重复"凭推断开工"的错误（参见 PROMPT_COST_ANALYSIS 的 E1/E2/E3 教训）；
- L1 只需改一个配置项且**完全本地**，风险与成本都低；但其**质量门槛必须 A/B 验证**，不能默认通过。

**明确不建议现在做的**：直接把抽取切到云端（隐私是产品决策，且 P0-S1 的 provider seam 已就位，可随时 opt-in）。
